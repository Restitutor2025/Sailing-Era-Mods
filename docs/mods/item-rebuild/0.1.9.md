# Item Rebuild 0.1.9 — 장비 묶음도 한 칸

2026-09-20. 사용자의 추가 요청에 따라 0.1.8의 장비 표시 묶음을 실제 가방 점유량 계산에도 적용했다. DLL은 기존 `Restitutor_Additional_Item_Rebuild.dll` 하나이며 0.1.8 결과는 evidence/0.1.8에 보존했다.

## 동작

동일 속성의 미장착 장비는 개수와 관계없이 한 칸이다. 일부 판매/삭제 후 하나라도 남으면 한 칸을 유지하며 마지막 장비까지 제거하면 그 칸이 빈다. 개별 GUID, 장비 상태, 실제 저장 행/Number와 원래 가방 최대 용량은 수정하지 않는다. 착용 중이거나 상태 확인이 불가능한 장비는 묶지 않는다. 장착하면 미장착 묶음과 별도 칸으로 계산되고, 해제 후 동일 속성 묶음에 다시 합류한다. 속성이 다른 장비도 별도 칸이다.

가방의 사용량/최대 용량과 가득 참 표시, PlayerBagDB.GetFreeCapacity, InnerAddItem 공간 검사, UIPropStore 동시 구매/판매 공간 검사에 동일한 논리 점유량을 적용했다. 미장착 장비 5개가 있는 가방에서 4개 판매는 빈 칸 0개, 5개 전량 판매는 빈 칸 1개다. 가득 찬 가방에도 같은 속성 묶음의 장비를 추가할 수 있다. 새로운 동일 장비를 한 번에 여러 개 받아도 새 묶음 한 칸만 필요하다.

원래 판매 슬라이더의 min=0, max=판매 가능 최대 개수는 유지한다. 구매품도 동일 속성 묶음으로 계산하므로 동일 장비 여러 개를 산다는 이유로 여러 칸을 요구하지 않는다. 아직 분류를 지원하지 않는 일반 아이템 구매는 원본의 단위당 한 칸 계산을 유지한다.

## 구현 계약

- `Capacity.cs`의 Occupied는 현재 가방을 읽어 장비/소모품 그룹 키를 세고, 나머지 행은 개별 계산한다. 장비 조회는 0.1.8과 같은 Unworn을 사용한다. 이벤트 경계에서 계산하며 지속 폴링은 없다.
- InnerAddItem 기존 전처리는 논리 점유량으로 공간을 검사한 다음 원본의 행 개수 검사를 해당 호출 인수에 한해 생략한다. 장비는 원본 추가 루프가 각각의 GUID를 생성한다. 소모품의 기존 수량 어댑터/백업/실패 복구는 유지한다.
- 기본 quality=-1은 설치 TemplateManager.GetCargo의 결과를 조회해 원본 PlayerItemData 생성자의 fallback(없으면 0)을 따른다. 신규 대상의 Supply=1, 구매가/특수 여부/상태를 포함한 동일 속성 기준을 유지한다.
- UIPropStore 거래 직전에 판매 후 남는 그룹과 구매로 생길 그룹을 함께 예측한다. 원본 Exchange는 `Capacity - 실제 행 수 >= BuyCount - SellCount`를 검사하므로, 해당 Exchange의 첫 SellCount 반환에만 `BuyCount + 실제 행 수 - 예상 점유량`을 넣어 비교식을 동치로 만든다. 실제 판매 선택/가격/Slot 수는 변경하지 않는다. 이후 SellCount 호출은 원래 수량이다.
- 원본 결제 루프는 구매부터 처리하므로 검증된 Exchange 실행 범위 안에서는 일시적인 추가 공간 검사만 생략한다. 저장된 Capacity를 임시로 올리거나 아이템 목록을 임시로 접지 않는다. Finalizer로 정상/예외 시 범위를 복원하며 Reset도 해제한다. 예외를 삼키거나 원본 거래 전체를 원자적이라고 가정하지 않는다.
- 추가 훅: PlayerBagDB.GetFreeCapacity 후처리, UIBagView.RefreshBagData 후처리, UIPropStoreModel.get_SellCount 후처리. Exchange는 기존 훅에 Prefix/Finalizer를 연결했다. 총 34개 고유 native 대상.

## 근거와 검증

**원본 본문 확인:** [0.1.9 증거](../../../ItemRebuild/evidence/0.1.9/)에 함수별 disassembly와 필드/서명을 보존했다. UIBagView.RefreshBagData는 실제 행 개수와 PlayerBagDB.Capacity로 표시를 생성한다. Exchange 0x143D475/0x143D48B에서 BuyCount/SellCount를 직접 호출하고 0x143D515~0x143D51B에서 공간을 비교한다. Sort 로컬 함수는 구매를 먼저 추가한 뒤 판매 GUID를 제거한다. ConfirmExchange는 확인 후 Exchange로 들어가며 RewardUtils.GainItem은 PlayerBagDB.AddItem으로 연결된다. ItemBagData.get_Capacity는 GetCargoTotalCapacity와 RVA를 공유하므로 둘 다 패치하지 않았다.

**정적 검증:** 설치 GameAssembly SHA256는 0.1.8과 같은 `50d53d17829e3e77b9786ea42d998d1ad258f0653846524069f22e5e442effca`. Release 경고/오류 0. 고유 훅 34개, 같은 RVA 별칭 없음. interop/game/Unity 참조 219개 및 모든 핸들러 서명 해석 통과. 시작 호출 그래프 7개에서 UIManager/지연 경계 접근 없음.

**오프라인 대역:** 3,943개 assertion 통과. 장비 5개 중 0~5개 판매, 같은 묶음/다른 묶음 구매, 가득 찬 가방 추가 획득, 새 묶음 일괄 획득, 장착/해제, 품질 차이, 화면 용량, 실제 원본 비교식과 논리 점유량의 동치, 일회성 SellCount 보정, 예외 후 범위 해제를 검사했다. GUID/Number/저장된 Capacity 불변을 확인했다. 저장 사본 389→280행 및 종류별 총수량 보존 검사도 유지한다.

**한계:** 게임·Steam을 실행하지 않았고 사용자 실전 보고는 아직 없다. 모든 모드의 인라인 공간 검사나 동적 개입을 완전히 조사한 것은 아니다. 특히 다른 모드가 Exchange의 첫 SellCount 호출 순서를 바꾸거나 거래 도중 재고를 추가로 변경하면 함께 재검토해야 한다. 실전 가방 표시/획득/구매/판매/장착/저장·재로드 확인은 사용자 몫이다. 장착으로 묶음이 분리되어 한도를 넘더라도 기존 장비를 삭제하지 않으며 신규 묶음 추가를 제한한다.
